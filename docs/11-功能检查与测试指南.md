## 本次修复

- 注册时手机号为null/留空被错误识别为字符串“null”。
- 无类别回收物品无法完成：改用默认积分系数1，并允许回收记录无类别。
- 极小重量积分四舍五入为0时违反正数约束：允许回收记录0积分，不生成0分积分流水。
- 取消回收预约后无法重新提交：复用已取消的预约记录重新申请，保留现有一物一回收订单关系。
- 回收申请未校验物品归属、审核状态和回收点是否开放。
- 已结束回收订单可被跳步/重新设置状态。
- 交易创建/完成、评价和审核缺少事务保护；添加事务和关键记录锁。
- 交易金额可被请求覆盖：出售按物品价格，赠送为0。
- 卖家确认后物品状态未同步；现在同步为PROCESSING。
- 修改已审核物品可绕过审核：修改后重新待审核，交易中的物品禁止修改。
- 我的物品受大厅分页/搜索影响：改为独立读取本人全部物品。
- 未分类物品没有计入分类看板：增加“未分类”统计。
- 建表脚本遗漏信誉流水与评价表，旧数据库缺少审核字段和约束：补全新库脚本及保留数据的启动升级。

## 表之间的关系

| 表 | 对应关系 |
|---|---|
| users | 物品发布人、交易双方、回收申请人、积分和信誉流水用户 |
| categories | 物品和回收记录可选类别；无类别回收默认每kg系数1 |
| items | owner_id关联users；reviewed_by关联审核管理员；photo_url保存图片访问地址 |
| trade_orders | item_id关联items，seller_id须等于物品发布人，buyer_id为另一用户 |
| recycling_orders | 关联物品、申请人和回收点；申请人须为物品所有者；一物品至多一个预约记录 |
| recycling_records | 每个回收订单至多一个完成记录，记录重量、金额与积分 |
| eco_point_records | 关联用户及回收完成记录，总和应等于users.total_points |
| reputation_records | user_id为外键；source_id是业务来源编号，不是单一表外键 |
| trade_feedback | 每个交易最多一次评价，评价人须为完成订单的买家 |
| recycling_stations | 为回收预约提供回收点 |

图片文件存储于启动后端时的工作目录下`uploads/photos`，数据库保存`/api/photos/...`地址。更改IDEA的工作目录可能导致旧图片无法读取。

## 手动测试顺序

1. 在IDEA停止并重新启动后端，等待启动成功；刷新前端。启动升级不删除原有数据，旧PENDING物品将进入待审核。
2. 用test_seller发布一件出售物品，价格25元，填写描述，选择交易星期（周一至周日）、时间（08:00至21:00，页面半小时一档）和地点（南苑/北苑的一站式/食堂），上传JPG/PNG（<=5MB），检查“我的物品”为待审核，买家大厅不可见。星期和时间是卖家预设的交接安排，不包含具体日期；平台没有在线支付功能。
3. 用admin审核通过；test_buyer在大厅查看完整描述和图片、申请交易。
4. test_seller在交易订单点击“确认交易”；test_buyer点击“确认完成”，双方订单已完成，物品不再出现在大厅。管理员没有交易操作按钮。
5. 另发布一件赠送物品测试0元交易；另发布一件出售物品测试撤回，撤回后应重新出现在大厅。
6. 发布一件物品，由管理员填写原因驳回；检查审核意见和信誉-5。信誉低于90时发布、交易申请、回收申请被拒绝。
7. test_recycle发布RECYCLE物品，审核通过后选择回收点、用日历选择未来预约日期，再从下拉列表选择08:00—21:00的时间点（间隔30分钟）并提交；管理员依次确认预约、开始处理、录入2kg并完成。无类别时获得2环保积分。
8. 另外一件回收物品测试撤回后重新预约，不能重复发放积分或重新处理已完成订单。
9. 在IDEA数据库控制台执行integrity_check.sql。新生成的异常应为0；若历史记录已有异常，先检查具体来源，不要直接删除或重建数据库。

不同浏览器/隐私窗口可同时登录不同账号；同一浏览器普通窗口共享localStorage，会互相覆盖登录账号。若只用一个窗口，退出后切换账号测试即可。

## 如何执行数据库完整性检查

这是一份只读的数据库体检脚本，不是项目启动步骤，也不会删除、修复或重建数据。建议完整测试结束后、提交课程设计前执行一次。自动化测试使用模拟数据库，实际数据库结构和历史记录还需单独核对。

1. 如果IDEA有Database（数据库）工具窗口：添加MySQL数据源，主机localhost、端口3306、数据库campus_recycle；用户名和密码采用自己实际配置的数据库账号。测试连接成功后打开该数据源的查询控制台。
2. 打开database/integrity_check.sql，将内容复制到查询控制台，选中全部SQL并执行。如果提示执行范围，选择全部语句。
3. 前三个结果分别展示表、字段和外键，它们不是异常数量，不要求显示0。后续结果中的issue是检查项目，anomalies是异常记录数；理想结果是所有anomalies都为0。
4. 若IDEA没有数据库工具窗口，可在已登录的MySQL命令行中输入：`source E:/code_all/GreenCampusSystem/database/integrity_check.sql;`，也可用MySQL Workbench运行同一脚本。
5. 异常数大于0时保存issue和数量，查明具体记录和原因后再处理。例如trade_parties检查卖家是否是物品发布人、买卖双方是否相同；eco_points_total检查用户环保积分总额是否与流水一致。不要为了得到0而直接删除历史数据。

全部为0只表示脚本覆盖的检查未发现异常，不能证明所有功能和全部数据库约束都已验证。

## 编辑物品验收

1. 卖家打开“我的物品”，对待审核、已驳回或已上架物品点击“编辑物品”。检查原描述、价格、图片和交易安排已回填。
2. 修改描述、出售价格、实拍图和交易星期/时间/地点，点击“保存并重新审核”。物品应变成待审核，原审核意见清空，刷新大厅后不可见。
3. 管理员重新审核通过后，买家查看详情应看到新描述、新图片、新价格及新安排；申请订单应采用新价格和新交易安排。
4. 买家申请后，以及交易处理中、已完成时，“我的物品”不显示编辑按钮；即使直接调用修改接口，后端也应拒绝。其他用户不能编辑该物品。
5. 编辑时点击取消，原信息不变；图片替换上传失败应保留原图片。移除图片并保存后，详情显示未上传实拍图。赠送和回收价格固定为0。
