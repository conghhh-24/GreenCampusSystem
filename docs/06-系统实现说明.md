# 系统实现说明

本文依据当前前后端代码及 `database/schema.sql`，说明实际实现与升级边界；数据库结构详见 [逻辑结构](04-数据库逻辑结构.md)。

## 前后端与接口

前端使用 Vue 3、Element Plus 和 ECharts，提供物品大厅、我的物品、交易订单、回收预约、积分、管理员中心和统计看板。`frontend/src/api.js` 统一发送会话 Cookie、CSRF 令牌和错误提示；Vite 将 `/api` 请求代理至后端。

后端使用 Spring Boot 和 JdbcTemplate，以参数绑定执行带用户输入的 SQL。`AuthController` 与 `AuthInterceptor` 负责会话和权限，`ApiController` 处理主要业务，`PhotoController` 保存图片，`StatisticsController` 在可重复读的只读事务中聚合统计。

| 接口组 | 当前行为 |
| --- | --- |
| `/api/auth/*` | 登录、读取当前身份、退出；注册为 `/api/auth/register` |
| `/api/items`、`/api/items/{itemId}` | 物品查询、发布、编辑、逻辑下架 |
| `/api/trades`、`/api/trades/{tradeId}/*` | 交易查询、申请、确认、完成、撤回和评价 |
| `/api/recycling-orders` 及其子路径 | 回收预约、状态处理、撤回和完成 |
| `/api/categories`、`/api/recycling-stations` | 读取类别和开放回收点 |
| `/api/points`、`/api/admin/*` | 本人积分、管理员审核和数据查询 |
| `/api/photos`、`/api/stats/overview` | 图片上传/读取、统计汇总 |

物品列表支持名称关键字、类别、处理方式、状态及分页筛选，按发布时间倒序固定排序，没有自选排序接口。大厅只返回已审核上架物品；我的物品按本人身份读取。分页页码从 0 开始，每页最多 50 条。

## 身份与权限

密码以 PBKDF2 哈希保存，启动时兼容迁移旧明文密码。登录成功更换会话，30 分钟无操作过期。后端从会话取得当前身份，核对请求中的 `ownerId`、`buyerId`、`operatorId` 等字段，不能仅修改编号冒用其他用户。每次受保护请求还会检查账号是否处于 ACTIVE 状态。

登录与注册要求 `X-Requested-With: XMLHttpRequest`；登录后的写请求校验 `X-CSRF-Token`。管理员接口和涉及审核、回收处理的操作另行校验 ADMIN 角色。图片 GET 允许未登录读取，上传仍需登录及写请求校验。

## 物品、交易与评价

发布和编辑必须选择已有类别。出售价格必须大于 0，赠送和回收价格为 0。出售/赠送还须填写未来的具体日期、08:00—21:00 内的整点或半点，以及限定校园交接地点；后端按北京时间复查。图片存储规则见 [开发环境](05-开发环境.md)。

新物品状态为 `PENDING_REVIEW`，管理员通过后为 `APPROVED`，驳回为 `REJECTED` 并记录意见。允许编辑的物品保存后重新待审核，原审核信息清空；已申请、处理中或已完成物品不可编辑。下架采用 `OFFLINE` 状态保留记录。

交易正常流程为 `APPLIED → PROCESSING → COMPLETED → REVIEWED`：买家申请，卖家确认，买家完成，买家评价。创建订单时锁定物品并复查状态、归属、处理方式和交接时间，订单金额、方式及交接安排取自物品，作为申请时快照。买卖双方可撤回尚未结束的订单；订单转为 `CANCELLED`，符合条件的物品恢复上架。

评价只允许已完成订单的买家提交一次，评分为 1—5 的整数，文字可空且最多 255 字。事务中先锁定订单，再保存评价、更新为 `REVIEWED` 并调整卖家信誉；4—5 分加 2，1—2 分减 2，3 分不变。唯一约束防止一笔订单重复评价。列表返回评分、文字和是否可评价，卖家与管理员可查看。评价不改变物品的 `COMPLETED` 状态，也不改变环保积分。

## 回收、环保积分与信誉

回收仅允许物品所有者对审核通过的 RECYCLE 物品申请，须选择开放回收点和未来预约时间。预约按北京时间限制为 08:00—21:00 的整点或半点。管理员依次将预约从 `APPLIED` 确认为 `APPOINTED`、开始 `PROCESSING`，最后录入正重量完成为 `COMPLETED`；普通用户不能代办完成。已取消预约再次申请时复用原记录，保持物品与预约的一对零或一关系。

完成事务同时更新预约和物品状态、生成唯一回收完成记录、写入正积分流水并增加用户余额。积分按 `Math.round(重量 × 类别系数)` 计算，历史空类别使用系数 1。结果为 0 时仍保留完成记录，不生成 0 分流水。重量、类别和所得积分保存在完成记录中。

环保积分用于记录回收贡献，`users.total_points` 应与环保流水之和一致。信誉分初始为 100，审核驳回减 5，低于 90 限制发布、交易申请及回收申请；信誉读取时按每满 10 天恢复 1 分。当前时间恢复不逐笔写信誉流水，因此不能用信誉流水之和直接核验全部信誉分。

## 已有数据库的启动升级

| 机制 | 实际范围 |
| --- | --- |
| `SchemaUpgrade` | 补具体交接日期、时间、地点及审核字段；修复旧 PENDING 与无有效订单占用的物品状态；兼容回收空类别、零积分；补审核人外键并更新类别视图 |
| `ApiController` 启动初始化 | 兼容增补图片、交接及信誉字段，创建缺失的信誉流水与评价表，并调用评价状态迁移 |
| `TradeFeedbackSchema` | 扩展订单状态 REVIEWED，将已有评价的 COMPLETED 订单修正为 REVIEWED；不重复写评价和计分 |
| `AuthController` 启动初始化 | 将未编码的旧密码迁移为 PBKDF2 哈希，原登录密码保持不变 |
| 手动脚本 | `trade_feedback_status.sql` 可在停服时迁移评价状态；`remove_unused_fields.sql` 为旧字段存档及删列的一次性操作，不能反复运行 |

启动升级不重建整个数据库，也不会自动删除 `meeting_day` 或六个未用字段；旧星期不能恢复唯一日期，旧物品需补选日期并重新审核。增量建表不保证历史库已经拥有新建库脚本的全部 CHECK，须以实际定义和 [完整性检查](07-数据库完整性说明.md) 为准。

当前没有类别/回收点维护页面、账号启停页面、在线支付、聊天和通知。业务验证步骤与测试范围见 [功能检查指南](11-功能检查与测试指南.md) 和 [测试说明](09-测试说明.md)。
