# 数据库完整性

以下以 `database/schema.sql` 和当前业务代码为准；真实验收库需另行核对约束是否已部署。

| 完整性类型 | 实现 | 项目示例 |
| --- | --- | --- |
| 实体完整性 | PRIMARY KEY | 10 张业务表均以自增 id 唯一标识记录，主键不为空、不重复 |
| 参照完整性 | FOREIGN KEY | 16 条外键保证引用用户、物品、订单、回收点和记录存在 |
| 用户定义完整性 | NOT NULL、UNIQUE、CHECK、ENUM | 订单评价唯一、预约完成记录唯一、评分 1—5、重量大于 0、金额非负、合法状态集合 |

默认值用于初始化数据，本身不能代替合法性约束。可空外键允许 NULL，非空外键才要求必须关联父记录。`UNIQUE(recycling_order_id)` 与外键共同保证每个预约至多一条完成记录；仅有外键不能保证一对一。

## 删除行为

外键未配置 ON DELETE CASCADE，InnoDB 默认限制删除仍被引用的父记录。因此用户存在物品或订单等历史引用时，直接删除通常会被外键拒绝；不能回答“用户删除了，订单一定保留”。页面撤回使用 OFFLINE 或 CANCELLED 等状态，保留历史记录。

## 外键之外的业务规则

外键只能保证所引用记录存在，不能保证审核人是管理员、卖家是物品发布人、买家不是卖家、评价人是订单买家或状态流转合法。后端必须检查身份、归属、价格、具体交接日期和回收预约时间。

两个用户同时申请同一物品时，事务内通过 SELECT ... FOR UPDATE 锁定该物品行。第二个请求等待后取得锁，仍要重新检查审核结果、物品状态、处理方式、归属和交接时间。状态是判断依据，真正的互斥来自数据库行锁；事务负责将检查、订单插入和物品状态修改共同提交或回滚。

评价事务先锁定订单，再验证已完成、买家身份和是否已有评价；插入评价、更新 REVIEWED 状态与信誉变更一并提交。trade_feedback.trade_id 的 UNIQUE 是重复评价的数据库兜底。

## 核对

`database/integrity_check.sql` 只读检查孤儿记录、交易双方、状态与完成记录、评价与 REVIEWED 状态、环保积分总额等；所有异常为 0 只表示脚本覆盖的规则未发现异常，不能代替完整业务测试。环保余额应按用户与 eco_point_records.change_points 的总和核对；信誉分还包含尚未写流水的时间恢复，不能照搬该核对公式。
