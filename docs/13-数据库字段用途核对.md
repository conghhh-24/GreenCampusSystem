# 数据库字段用途核对

## 本次精简范围

根据页面、接口、统计与业务校验核对，以下6个字段没有形成实际业务功能。当前代码、建表脚本和演示数据已移除其依赖；本机已有数据库由用户执行 `database/remove_unused_fields.sql` 删除，应用启动不会自动删列。

| 表 | 删除字段 | 精简原因 |
| --- | --- | --- |
| `items` | `original_price` | 无原价输入、展示及成交计算用途 |
| `items` | `estimated_recycle_price` | 无估价算法、展示及回收结算用途 |
| `items` | `condition_level` | 无成色选择、展示、筛选，原页面发布默认GOOD |
| `recycling_records` | `recycle_amount` | 原页面完成回收固定传0，无金额录入、展示或统计 |
| `recycling_stations` | `accepted_categories` | 无展示，也未用于限制可接收的物品类别 |
| `recycling_stations` | `phone` | 回收预约页面只使用名称、位置，没有使用回收点电话 |

本次没有连接本机MySQL执行删除，也未据此断言旧值都为0。迁移脚本先将旧字段与记录id保存到3张 `backup_*_20261102` 存档表，再删除业务表字段。这些是存档表，不参与业务流程。

执行顺序：停止后端；逐条执行迁移脚本，任一句失败即停止；全部成功后启动更新后的后端并刷新前端。已有数据不要重新执行 schema.sql 或 init_data.sql。删除命令仅执行一次。脚本末尾核对删除结果，应返回0行。

## 有后端用途但页面入口不完整的字段

| 字段或表 | 实际用途与缺口 |
| --- | --- |
| `items.category_id`、`categories.name` | 关联类别，后端支持类别查询与分类统计；但当前发布接口固定写入NULL，页面没有类别选择，新物品是未分类 |
| `categories.point_factor` | 完成回收时按“重量kg × 类别系数”四舍五入发放环保积分；未分类采用系数1。分类系数有用途，不能仅因页面缺入口就删除 |
| `recycling_records.category_id` | 保存完成回收时的类别。未分类物品的记录为NULL，仍有类别追溯用途 |
| `trade_feedback` | 有提交评价接口、每单一次与买家身份校验；评分可影响卖家信誉。但缺少页面提交和查看入口 |
| `users.status` | 登录、会话和操作权限会使用ACTIVE；缺少页面停用/启用入口 |
| `recycling_stations.status` | 控制可选回收点并在提交预约时校验；缺少回收点管理页面 |

## 应保留的属性和冗余

- `items.current_price` 是现价，也是出售订单金额来源；赠送和回收为0。
- `trade_orders.amount`、处理方式和交接日期/时间/地点是申请时快照，不应随物品未来修改而改变。
- `users.phone` 用于注册校验、唯一约束与管理员查询，本次不删除。
- `users.total_points` 是环保积分余额，`eco_point_records` 是流水，完成回收时在同一事务维护。
- `recycling_records.contribution_points` 保存当次实际发放分数，不能根据未来类别系数重算历史积分。
- `reputation_score/reputation_bonus_at` 参与低信誉操作限制与时间恢复；`reputation_records` 用于变更追溯。时间恢复目前不单独写流水。
- 发布、申请、预约、完成、实际回收等时间表示不同事件，分别用于页面、排序、月度趋势和平均处理天数。
- 主键、外键、审核人/审核时间和创建时间承担标识、关联、约束与追溯作用，不能仅因没有页面输入框就判断为多余。
- 旧数据库可能保留 `meeting_day`，用于历史订单显示；新流程使用 `meeting_date DATE`，本次不删除旧星期记录。

核对依据：`frontend/src/main.js`，后端 `ApiController`、`StatisticsController`、认证类，以及 `database/` 中的建表、视图、查询和演示数据脚本。`database/field_usage_check.sql` 可只读检查精简状态和当前数据分布。
