## 结构说明

当前业务仅向 `items.meeting_date` 和 `trade_orders.meeting_date` 写入具体日期，不向 `meeting_day` 写入。旧星期不能推算出唯一日期；旧物品需编辑补选日期并重新审核，已有订单日期不自动回填。验收库是否仍有旧列须单独核查。

索引中的普通MUL标识不代表唯一。图中基数根据单列唯一索引与外键可空性确定。

## 检查约束与跨表规则

| 字段 | 建表脚本中的 CHECK |
| --- | --- |
| `users.total_points` | 大于等于 0 |
| `categories.point_factor` | 大于 0 |
| `items.current_price`、`trade_orders.amount` | 大于等于 0 |
| `recycling_records.weight_kg` | 大于 0 |
| `recycling_records.contribution_points` | 大于等于 0 |
| `trade_feedback.rating` | 1 至 5 |
| `eco_point_records.change_points` | 不等于 0 |

所有外键均未声明级联删除；InnoDB 默认限制删除仍被引用的父记录。外键不能保证卖家等于物品所有者、评价人等于订单买家、审核人为管理员或状态流转合法，这些由后端校验和事务保证。历史库是否具备上述 CHECK 需核对实际建表定义。

## 范式与保留冗余

各表属性按单值保存，满足第一范式；当前候选键均为单列，不存在对复合候选键的部分依赖，满足第二范式。不能笼统宣称全部表严格满足第三范式：例如 `trade_orders.item_id` 可确定物品所有者，`trade_feedback.trade_id` 可确定买家，当前分别重复保存 `seller_id` 和 `buyer_id`。`recycling_orders.applicant_id` 也在仅允许本人回收的规则下可由物品推导。

订单金额、处理方式和交接安排属于申请时快照；回收类别与贡献积分属于完成时快照；`users.total_points` 是流水汇总的受控冗余。这些字段须明确语义并在事务中保持一致，不能用“有主键”直接证明第三范式。逐项判断见 [字段用途核对](13-数据库字段用途核对.md)。
